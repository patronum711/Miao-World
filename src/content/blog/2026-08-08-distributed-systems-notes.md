# 分布式系统简介

PS：只要评价对比类的题目，就思考本节的角度来回答。

## 定义与特征

定义：一群独立计算机的集合，但在用户看来是一个单机系统

特征：

1.组件被所有用户共享（除了系统资源）

2.没有全局时间：每个节点有自己的时钟，步调不一致

3.多点控制与失效：允许多处控制，也允许多处失效而整体不瘫痪

4.软件运行在节点甚至计算单元上

## 实现目标

1.资源访问便利

2.透明

3.开放

4.可拓展

## 透明性

<img src="../../blog-assets/2026-08-08-distributed-systems-notes/image-001.png" alt="image 001" />
完全透明不可取：性能不好（一致性不好维护），不好（无法区分挂了还是运行慢）

## 开放性

含义：系统根据准则来提供服务，有规定的语法

要求：实现策略与机制的分离

机制：提供某种功能的具体手段（具体的工具）

策略：决定如何使用这些机制的准则（抽象的设计）

## 可扩展性

三个维度：

规模 (Size)：用户数量和资源数量增加

地域 (Geography)：节点之间的最大物理距离

管理 (Administrative)：管理域的数量增加

实现技术：

隐藏通信延迟：异步处理，减少等待 。

分布：将组件拆细，如 DNS 将域名空间划分为不同区域 。

复制/缓存：设置副本服务器或数据缓存，但难点在于一致性维护 。

## 分布式计算系统分类：集群系统、网格系统、云系统

集群 (Cluster)：同构的（OS 和硬件相似）、通过LAN连接、有单个管理节点 。

网格 (Grid)：异构的（分布在各地）、包含多个组织、容易扩展到广域网 (WAN) 。

# 体系结构

## 体系结构分类及特点

软件体系结构：逻辑上的组织。关注组件、之间的交互、组织

1.分层结构（Layered）

2.基于对象（Object-based）

3.资源中心（REST）

4.基于事件（Event-based）。

系统体系结构：物理上的组织。关注组件、之间的交互、组建位置

1.集中式（Client-Server）：有一个集中的控制节点

2.非集中式（P2P）：没有集中的控制节点，各节点独立运行，地位等同

3.混合式：两者均包含。

## 软件体系结构：分层结构

例子：应用三层结构（常用于集中式系统）

1.用户界面层（界面显示、交互）

2.处理层：核心业务逻辑

3.数据层：持久化存储（文件系统、数据库）

## 软件体系结构：基于对象

对象组件间通过过程调用相互连接。

## 软件体系结构：基于资源

资源组建的集合，应用可通过RESTful API对资源进行增删查改。

## 系统体系结构：分布式（P2P模型）

### 结构化P2P

描述：通过分布式哈希表 (DHT) 将节点组在Chord网络。

一个Chord环共2^m个节点，包含的要素：

实体：m位标识符，共2^m个。用k标识。

节点：每个实际节点，由m位进行标识。用p标识。

实体实际存储在顺时针的后继succ节点中

（考点）指纹表计算逻辑：

每个实际Node的指状表包括m项，第i项的值为：

<img src="../../blog-assets/2026-08-08-distributed-systems-notes/image-002.png" alt="image 002" />
（考点）查询/搜索过程（效率为O（log n））：

节点p要查找实体k。

1.首先检查k是否落在p和succ(p)之间，如果是，直接返回succ(p)

2.在p的指状表查找j，使得FTp(j)<= k < FTp(j+1) (j为FT的索引)

3.将查找请求转发给节点q=FTp(j)

4.如此循环1、2、3，直到找到。

（考点）节点加入：

1.寻找位置：新节点p联系已有节点（任意），找到p的后继节点S = succ(p)

2.更新自己的FT：请求S协助，通过多次查找，初始化自己的FT

3.更新其他的FT：节点p会逆时针寻找并通知节点（应指向p，但目前指向S的节点）更新其指状表条目。

3.数据迁移：将部分数据从S迁移到p（之前没迁移实体数据）

（考点）节点退出：

1.通知邻居：告知前驱节点和后继节点，让它们直接相连。

2.移交数据：将自己负责的所有键值数据全部返还给后继节点，确保数据不丢失。

3.指状表更新：其他节点在后续的周期性检查（稳定化过程）中会发现该节点已离开，并更新指状表。

（考点）节点失效（非正常，不通知，直接离开Chord）：

应对机制：系统通过周期性的stabilize消息检查前驱/后继的存活状态，动态修复指状表和环结构。

好处：简单、易扩展、效率高（FT）、容错性强

### 非结构化P2P

描述：节点之间随机连接

搜索方式：

洪泛 (Flooding)：请求节点向它所有邻居节点发出数据搜索请求，如果已经收到过就会被忽略，否则就会在本节点中查找数据项，迭代传递

随机游走：请求发送节点u从邻居节点中随机选择一个节点，然后进行本地搜索，如果没有完成，就继续随机选一个邻居继续搜索，直到搜索到达目标或终止情况。

### 超级对等节点

如何缺定超级对等节点：更多的资源（CPU内存）、更高的网络带宽、更稳定。它对外是一个对等节点（和其它超级节点平等）；对内则像一个“小型服务器”，管理着一群普通节点。

好处：解决了搜索效率低的问题（普通非结构P2P）：解决了C-S模型单点失效。

搜索：普通节点会通过超级节点搜索

### 中间件

处于应用程序和操作系统、本地网络之间的软件层。

目标（总体：实现开放性）：

1.屏蔽底层异构性

2.实现透明性，为应用提供统一接口

### 分布式系统自我管理

自我管理的核心目标是建立具体有以下特点的分布式系统：

自我配置 自我优化 自我恢复 自我保护

# 进程与虚拟化

## 进程与线程

进程：由操作系统分配资源（内存、文件等）的独立单位。进程切换代价高。

线程：最小的可执行一系列指令的软件处理器。共享进程的资源。在进程上下文执行。

上下文：

– 处理器上下文：栈指针、地址寄存器、程序计数器等；

– 线程上下文：处理器上下文、状态等。

– 进程上下文：线程上下文、MMU寄存器值、TLB等；

为什么分布式系统爱用（多）线程？

避免阻塞：单线程服务器处理 I/O 时会卡住。多线程可以让一个线程等 I/O时，另一个线程继续算。

高性能/：线程创建、销毁和切换的代价远小于进程（不需要切换地址空间）。

并行性：在多核 CPU 上，多线程能真正同时干活。

## 虚拟化

概念：虚拟化的本质是在硬件之上加了一个“模拟层，让软件觉得自己跑在独立的硬件上。（中间件理论的实现）

好处/为什么（包括中间件好处1）：

1.应用软件适配：屏蔽了底层硬件的异构性+实现透明性提供统一接口

2.可移植性：方便代码迁移（例如JVM）

3.隔离性：虚拟机GeustOS被攻击不会影响到物理机上的其他系统

主要方式：

1.进程虚拟机：运行于Host OS之上。一个解释器，提供一个独立的指令集，对指令解释运行，如JVM。(位置：Host OS之上) 特点：性能差，隔离性弱

2.原生虚拟机监控器：物理硬件之上，中间没有操作系统。 模拟为多套虚拟硬件，并可以在其之上安装不同的Guest OS。特点：高性能，隔离性强

3.主机虚拟机监控器：Host OS之上，作为一个特殊的应用运行。利用HostOS的能力简化VMM实现，其上可安装不同GuestOS 特点：性能差，易于部署安装

## 客户与服务器（集中式系统体系结构C-S）

### 服务器的状态：

1.无状态：服务器不保存客户信息

优点：不存在可靠性问题，坏了重启就行。

缺点：每次请求需要携带所有信息。

2.有状态：服务器维护客户的会话信息。

优点：通信量小（不用每次发重复信息），性能可能更高。

缺点：存在可靠性问题。如果服务器挂了，客户的状态就丢了。

### 服务器发现

问题：客户端找到服务器的IP和端口

1.静态分配

客户端预先知道服务器的地址和端口（例如Http默认80）

缺点：缺乏灵活性，服务器一旦更换就找不到了

2.目录服务守护进程

服务注册：服务器启动，向守护进程（Daemon）注册自己的端口号，存入端点表

客户端请求：客户端首先联系该守护进程，询问某个服务的端点（端口），获取端口后，客户端直接向真正的服务器发起业务请求

3.超级服务器

超级服务器监听多个端口，收到请求后，根据端口号创建对应的服务器进程，然后客户端与这个服务器进程进行对话。

优点：服务器不常驻运行

缺点：相应速度较慢，依赖单点服务器

### 服务器集群与请求分发

分布式服务器还可以分为三层：

1.逻辑交换机：接受请求，分发给后端服务器

2.应用计算服务器

3.数据持久层：数据库或文件系统

分发策略：

A 传输层分发（性能）

1.轮询：按顺序分发给服务器

2.基于服务类型：根据端口号分发

3.基于负载：分发给负载最低的服务器

B 基于内容分发（效率）

C 混合（性能好+精准）

## 代码迁移

把正在跑的程序从 A 机器搬到 B 机器。

作用/目标/为什么：

1.负载均衡（将负载高的节点上运行的程序迁移到负载低的节点）

2.减少通信开销（移动代码，而不是移动数据，代码更小）

3.动态配置：按需动态请求下载

4.移动代理

代码迁移模型：代码段（指令）、资源段（文件/链接）、执行段（寄存器/栈状态）。

代码迁移分类

分类1:

弱迁移：只迁“代码段”。重启执行。

强迁移：迁移“代码段 + 执行段”。继续执行。

分类2:（接受者为代码实际执行者）

发送者发起（Push）

接受者发起（Pull）

涉及的问题：

1.资源与机器的绑定程度（注意：不是代码和资源的绑定程度）：

问题：数据迁移了到了机器B，资源在机器A上不一定可迁移。

| 资源类型 | 绑定强度 | 典型例子 | 迁移时的处理方式 |
| --- | --- | --- | --- |
| 未连接 (Unattached) | 弱 | 独立的数据文件、文档 | 搬走 (MV) 或 复制 (CP)：因为它跟机器没啥关系，搬走最省事。 |
| 紧固 (Fastened) | 中 | 本地数据库、特定库文件 | 建立全局引用 (GR)：数据太大搬不动，代码在 B 机器通过网络“远程访问” A 的数据。 |
| 固定 (Fixed) | 强 | 本地硬件（如打印机） | 重新绑定 (RB)：代码到了 B 机器，自动连接 B 机器的打印机。 |

2.异构系统迁移

问题：

1.运行环境不兼容

2.进程/线程/CPU上下文依赖于硬件

解决（加入虚拟层VMM）：

1.进程虚拟机（代码编译为中间码，由进程虚拟机（解释器）解释，每个机器上都安装进程虚拟机，例如JVM）

2.虚拟机监控器（包括原生虚拟机监控器和主机虚拟机监控器）

3.虚拟机迁移

静态迁移：停止当前的虚拟机，迁移内存，然后重新启动虚拟机；

动态迁移：将内存内容推送到新的机器，在迁移过程中重新发送被修改过的页面；在新的虚拟机上立即创建进程，并且按需拷贝内存页面；可能需要重复多次内存复制

# 进程通信

## 理论基础

1.物理基础：网络协议栈

2.分类：

瞬态：消息被即使发送接收，不存储

持久：消息被存储在通信服务器磁盘上，直到被接收

同步：发送者发出消息后，阻塞（直到对方收到或处理好）

异步：发送者发出消息后，不阻塞，继续执行

3.通信中间件

在OS和应用之间添加一个中间通信层（作用同通用作用）

4.三种通信模式

点对点通信：网络中任意两个用户之间的通信

多播：一个发送者将信息发送到网络中的指定多用户

广播：一个发送者将信息发送到网络中的所有用户

5.客户端/服务端通信

瞬态、同步

## 远程过程调用（RPC）

特点：瞬态、同步

定义：本地程序允许调用其他机器上的远程服务，且就像调用本地函数一样透明（模仿“本地过程调用”）

10个步骤：

Client进程调用普通的本地过程（Client Stub存根）。

Client Stub 将参数打包成消息（Marshalling/序列化），并调用本地操作系统。

Client OS 发送消息给远程操作系统。

Server OS 接收消息并将其交给 Server Stub。

Server Stub 将消息拆包（Unmarshalling/反序列化），提取参数。

Server Stub 调用真正的 Server 进程。

Server 进程完成计算，将结果返回给 Server Stub。

Server Stub 将结果打包成消息，调用本地操作系统。

Server OS 将结果消息发送回 Client OS。

Client OS 接收消息并交给 Client Stub，最后由 Client Stub 将结果返回给 Client 进程。

PS：序列化作用：为了解决异构系统带来的差异

### 多播通信

网络层成本太大，通过应用层来实现

1.基于覆盖网络的多播（Overlay-Based Muticast）

概述：将节点组织为树或者网格（虚拟连接）。鲁棒性差

例子：基于Chord的树（基于Chord来构建树）

1.确定根节点

发起者，生成多播标识符mid，succ（mid）为根节点。

2.加入节点

如果P想加入，将发送join（mid）给根节点（根据Chord规则前进，即相当于查找mid的规则），路途中会经过其他节点Q：

如果Q没有没有见过mid（即没有在树中），记录P是自己的孩子，并继续向上转发；如果Q见过mid（即在树中），添加记录P是自己的孩子，不再继续转发。

2.基于Gossip的多播

概述：Gossip 协议利用一种随机的方式将信息传播到整个网络中，并在一定时间内使得系统内的所有节点数据一致，不依赖固定的路径。鲁棒性强

三种基本范式 (P和Q之间的信息交换模式)

Push (推)：节点 P 主动将更新推给随机节点 Q 。

Pull (拉)：节点 P 主动从随机节点 Q 拉取更新 。

Push-Pull (推拉结合)：双方互相交换，信息扩散效率最高

两个运行模型：

1.反熵模型：节点 P 随机选一个节点 Q，然后交换所有更新（三种范式）

2.谣言传播模型

# 命名系统

## 核心概念

实体 (Entity)：分布式系统中的任何事物（主机、用户、文件等） 。

访问点 (Access Point)：访问实体的途径，其实就是一个特殊的实体 。

地址 (Address)：访问点的名称，用于定位实体 。

名字 (Name)：用于标识实体的字符串，是位置无关的（位置可以变，名字不变）

标识符 (Identifier)：一种特殊的名称，具有唯一性（一个标识符只对应一个实体，且不重复使用） 。

命名：实现名称-地址的绑定（有了地址就可以找到实体）

## 无结构命名

概念：无结构命名（又称平坦命名）的名字不包含任何位置信息。

方法：

1.广播（ARP协议）

2.转发指针：当实体移动，留下一个指向新位置的指针（SSP）

3.基于宿主地址（单层的转发指针）：宿主机始终记录实体的最新地址。客户端首先联系宿主机再联系实体地址。

4.分布式哈希表DHT（一种实现：Chord）

详见第二章。

5.分层定位（树结构，注意与下面区别，看有无命名空间字样）

概述：将网络划分为多个分层的域，每个域由目录节点表示，构建一棵大规模的搜索树

组成：

1.叶子结点：存储实体的实际地址

2.中间节点：存储指向子节点的指针

3.根节点：顶端（知道所有实体去向）

搜索过程：

1.从本地开始：请求首先发送到客户端所在的叶节点

2.向上搜索：如果该节点没有要搜索的实体记录，转发给父节点，直到找到一个知道该实体记录的节点（知道不等于存储）

3.向下搜索：沿着预设的指针一路向下，找到实际存储实际地址的叶节点。

插入过程：

1.插入请求被转发到知道实体 E 地址对的第一个节点；

2.建立一条从第一个知道实体 E 地址的节点到实体 E 的指针链

## 结构化命名

概念：按照一定规则进行命名，名称不再平坦无规律。

PS：路径名是名字，而不是地址。"/home/steen/keys"

命名空间/命名图：

叶节点：代表实际的实体，存储实体的地址、属性或状态信息 。

目录节点：有指向其他节点的边，每条边都有一个标签，类似于文件夹 。

根节点：命名图的起点。

名称解析：

给定名称（路径名），在命名图中搜索查找名称所指向的节点的过程。

闭包机制：

在哪启动（寻找初始目录节点）及如何启动名称解析的机制。

名称链接：

1.硬链接：路径名，可直接在命名图中按照路径搜索

2.软链接：特殊的叶节点，不存储实体的地址，而且存储另一个地址的绝对路径名（名字），再根据这个名字重新搜索。

挂载：

概述：将当前命名空间中的节点与另一个空间的节点标识符相关联

挂接点：当前命名空间中存储外部节点标识符

挂载点：外部命名空间中的目录节点

命名空间实现（三层命名空间模型）：

1.全局层：根节点及靠近根节点的目录节点。特点：稳定，代表组织群。

2.行政层：单个组织内被管理的目录节点。特点：相对稳定，代表同一组织单位，可用性要求最高

3.管理层：经常改变的节点组成。特点：变化频繁，终端用户维护，性能要求高

名称解析实现：

1.迭代式命名解析：客户端程序逐个询问服务器

客户端名称解析程序将完整的名称转发给根服务器，根服务器会尽力返回能解析的部分，然后客户继续将剩下的路径名转发到下一台名称服务器，该服务器再解析一部分名称，如此重复，直到查找到目标节点。

缺：不容易使用缓存策略进行优化

2.递归式命名解析：客户端将请求交给服务器后，后续的解析由服务器代劳

客户将名称解析请求发送到名称服务器后，名称服务器会把结果传递给它找到的下一台服务器，下一台服务器如果故需要的话会继续转发，直至完整的名称解析完成，然后返回客户。

优：缓存机制更有效（缓存在所有服务器上，可复用）；减少通信开销（服务器间通信距离更近）

缺：对名称服务器要求高

# 协同（同步）

## 物理时钟同步

概述：需要精确时间+顺序，要进行物理时钟同步

UTC：统一协调时间

同步算法的评价指标：

1.精度：两个机器的时钟偏差在特定范围内

2.准确度：机器时钟与UTC时间的偏差

两种同步类型：

1.内部同步：使用机器内部产生的同步信号，保证时钟的精度，即两个机器的时钟偏差在特定范围内

2.外部同步：使用外部时间源UTC，保证时钟的准确度，即机器时钟与UTC时间的偏差在特定范围。

PS：外部同步后，内部自然也就同步了

同步算法：

1.NTP算法（外部同步）

偏差=(T2-T1+T3-T4)/2 正数为慢

2.Berkeley算法（内部同步）

时间服务器（没有外部时间源），周期性地扫描所有的服务器，计算时间均值，并告诉其他机器如何调整当前时间，跳至新时间，或减速等待对齐（不能后退）

3.RBS（内部同步）

## 逻辑时钟

概述：只需要事件发生顺序，则可以使用逻辑时钟

### Lamport逻辑时钟

Happens-before/因果关系 a->b，规则：

1.进程内：如果a和b是同进程中两事件，并且 a在 b之前到达，则有：a->b

2.消息间：如果a是消息的发送事件，b是消息的接收事件，则a->b

3.传递性：如果 a->b 并且 b->c 则 a->c

4.并发关系：如果既不能证明 a→b，也不能证明 b→a，则称 a 和 b 是并发的。

Lamport逻辑时钟（算法）：

目标：为每个事件分配一个时间戳 C(e)，使得：如果 a→b，则 C(a)<C(b)

实现规则：

<img src="../../blog-assets/2026-08-08-distributed-systems-notes/image-005.png" alt="image 005" />
PS：发送消息，由于也是事件，需要先自增事件戳，然后携带事件戳发送消息。

应用1：全序多播（使用Lamport时钟）

1.进程P将加上时间戳（先自增本地）的消息发送到所有的进程，消息本身保存在本地queue

2.任何进程接收到消息（注意这里会可能更新本地时钟），放在queue中，并根据时间戳排序；向所有进程（包括自己）广播确认ACK

某个进程在满足如下条件才将消息交付给应用：

1.该消息在队列首

2.队列中包含对此消息的所有其他进程发送的ACK（全员确认）

缺陷：所有消息都按序发送，代价太高

应用2:逻辑时钟解决互斥访问（也利用了全许多播）

1.进程P想要进入临界区时，将带有时间戳的ENTER广播到所有进程，并保存在本地队列

2.任何进程接收到ENTER（接收消息可能更新时钟），放在队列中，并按时间戳排序；并向所有进程（包括自己）发送ALLOW确认

某个进程只有在满足如下条件，才进入临界区：

1.自己的Enter消息在队首

2.队列中包含对此ENTER的所有其他进程发送的ALLOW

### 向量时钟

为了弥补Lamport缺陷所设计的。

目标：为每个进程i分配一个向量VCi，VCi(i)是本地时钟，VCi(j)是i所认为的j的时钟，使得：a→b 等价于 ts(a)<ts(b)，即：

1. a向量的所有维度都 ≤b 向量

2.至少有一个维度严格<。

规则：

1.本地增加：Pi每发生一个新事件，本地VCi(i)自增

2.发送消息：Pi发送消息，携带事件戳ts(m)=VCi

3.接收消息：对向量每个角落维度取最大值，然后将本地VCi(i)自增

很好的例子（a中推导出m2<m4，可通过定义证明，利用传递性）

<img src="../../blog-assets/2026-08-08-distributed-systems-notes/image-006.png" alt="image 006" />
应用：因果有序多播（使用向量时钟）

优点：没有因果关系的消息（并发关系），在不同副本交付顺序不重要。性能更好。

发送时：进程Pi首先自增本地时钟VCi(i)，然后作为时间戳发出

接收时：消息到达后不立即更新时钟（整个向量），而是先进入缓冲检查。

检查：只有在满足交付条件并将消息交给应用层（真接收）后，才更新VC

交付条件：

Pj推迟“接受”来自Pi的消息m直到：

• ts(m)[i] = VCj[i] + 1  // m是Pj应该从Pi接收的消息

• ts(m)[k] ≤ VCj[k]，k≠ I   // Pj已经接受所有Pi在发送m时已经接受的消息

## 互斥

大体分类：

基于许可：如果进程需要访问临界区或者访问资源，需要从其他进程获得许可。

基于令牌：仅有的一个令牌在进程之间传递。拥有令牌的进程可以访问临界区或者将令牌传递给其他进程。

下面是另一种分类方式：

集中式（存在协调者）

非集中式（存在多个协调者）

分布式（不存在协调者）

令牌式

### 互斥算法：集中式（基于许可）

设置一个协作者Controller

流程：

请求：进程 P发送 REQUEST 给协作者

回复：如果临界区空闲，协调者回复 OK；如果被占用，协调者将请求放入队列，不回复。退出临界区，发送 RELEASE。协调者从队列取下一个进程发 OK。

优点：简单，每个进入/退出仅需 3 条消息

缺点：单点故障和性能瓶颈。

### 互斥算法：非集中式（处于之间，依然存在协调者）（基于许可）

像n个协作者（均具有管理权）申请访问。获得m>N/2个协作者的OK，才可以访问。

优点：减少了单个协作者失效，造成的影响

缺点：协作者宕机后恢复，可能忘记发出去的许可，导致再度颁发许可互斥失效

### 互斥算法：分布式Ricart & Agrawala（基于许可）

之前（Lamport解决互斥访问算法的优化版）

流程：

请求：Pi想进入，向所有进程广播Request（包含资源、i、时间戳）

接收：

1.若不在临界区且不想访问：回复OK（单播）

2.已在临界区：不应答，放入队列

3.不在临界区但想访问：比较时间戳

接收到的时间戳更早，OK；

自己的更早，放入队列

退出：向等待队列发送OK

缺点：单个故障点被n个故障点所取代， 故障概率高（当一个进程崩溃，不能回答请求，不应答被错误地解释为拒绝请求，阻塞了所有请求进入所有临界区地后续进程）。同时网络流量大大增加。进程维护开销较大，每次需要2(n-1)个消息。

### 互斥算法：令牌环算法

将进程组织成逻辑环（每个进程知道下游），令牌在这些进程之间传递。拥有令牌的进程进入临界区。

### 选举算法

背景：解决如何选择协作者的问题（有协作者的算法的前置条件）

假设：

1.所有进程有唯一ID

2.所有的进程都知道系统中的其他进程ID，但不知道是否允许

3.选举算法就是要找到具有最大ID的运行的进程

1.Bully算法

触发条件：任何进程 P 发现协调者不再响应。

算法流程：

1.P 向所有 ID 比自己大 的进程发送 ELECTION 消息。

2.如果有更高 ID 的进程回应 OK（表示它还活着），则 P 的任务结束，等待更高 ID 的进程去完成选举。

3.如果没有进程回应，说明 P 是当前活着的最高 ID 进程。

4.P 赢得选举，向所有进程广播 COORDINATOR 消息。

<img src="../../blog-assets/2026-08-08-distributed-systems-notes/image-007.png" alt="image 007" />
2.Ring算法

逻辑结构：进程按 ID 大小排列在一个逻辑环中，Pi的下游是 Pi+1

算法流程：

发现故障的进程P创建一个包含自己ID的ELECTION消息，传给下游（若下游挂了，则传给下下游，类推）

传递：每个进程收到消息后，将自己的ID添加到列表里，继续向下游传。

确定：消息绕环一圈回到发起者 P。P 查看列表，选出ID最大的进程。

通知：P发送COORDINATOR消息再绕一圈，通知所有人“谁是新领袖”以及在环中的节点

## 一致性模型（是要求）

进程和分布式的数据存储之间的一个约定。如果进程同意遵守某些规则，那么数据存储将正常运行。

### CAP理论

Concurrency一致性：要么读到最新数据，要么读取失败（不能读旧数据）

Available可用性：任何请求都可以得到响应

Partition Tolerant分区容忍性：消息丢失或延迟，系统仍然继续提供服务

### 以数据为中心的一致性

关注：全局一致性

使用场景：读写并重（计算密集型任务）

1.连续一致性

要求：

A. 所有进程必须看到完全一致的写操作顺序（通过读看到）

B. 在每个独立的进程内部，该进程所执行的所有操作在全局序列中出现的顺序，必须符合其程序指令的逻辑先后顺序。

2.因果一致性

更弱，认为只有因果关系的操作，才必须按顺序看。

要求：所有进程必须看到有因果关系的写操作顺序（并发关系则不要求）

### 以客户为中心的一致性

关注：单一客户一致性，只保证最终一致性（弱一致性）

使用场景：读多写少，内容分发（手机应用）

最终一致性：如果在很长一段时间没有更新操作，则所有样本都将逐渐成为一致。优点：避免写写操作冲突 缺点：达到一致所需时间长

要求/判定准则：

1.单调读

读取同一个值，只能是越来越新（不能读到旧数据）

2.单调写

写入同一个值，必须等上一次写操作完毕，才能执行新的写。

3.读写一致性

写后读同一数据，立即看到更新

4.写读一致性

读后写，保证写发生在所读值上。

## 一致性协议

### 连续一致性协议

限制数值偏差：

核心逻辑：服务器记录每一个写操作对数值的改变。

协议操作：每个服务器维护一个“视图”，记录它认为其他副本目前的状态。 当本地产生的更新超过一定阈值（如 val(W)>δ/(N−1)），或者发现自己落后太多时，就进行更新扩散（Gossiping）。

限制陈旧度：

核心逻辑：基于时间。

协议操作：服务器维护实时向量时钟（RVC）。 如果发现当前时间与上一次看到某副本更新的时间差超过了界限，就主动从该副本“拉取”新的写操作。

限制顺序偏差：

核心逻辑：基于本地暂存的“临时更新”数量。

协议操作：将本地写操作放入队列，当队列长度达到限额，必须先完成全局排序和提交，否则不再接受新操作。

### 主副本协议

背景逻辑：为了简单高效，规定每一项数据都有一个唯一的“班长”（Primary Server），所有写操作必须由班长点头。

远程写协议 (Remote-write)：

运行流程：客户端向任意副本发起写请求 → 该副本转发给主服务器 → 主服务器更新自己，并通知所有备份（Backup）更新 → 备份确认（ACK） → 主服务器告诉客户端写完了。

逻辑优势：实现顺序一致性非常简单，因为所有写操作在主服务器那里天然有序。

本地写协议 (Local-write)：

运行流程：当进程要写数据时，系统直接把数据的“主副本”地位迁移到该进程所在的服务器上。

逻辑优势：适合“移动办公”或一段时间内只有一个人频繁修改的情况。修改时不需要每次都跑远程中心。

### 复制写协议

背景逻辑：去中心化。不再设固定班长，写操作直接发给多个/所有副本。

主动复制 (Active Replication)：

核心逻辑：每个副本都运行一个相同的状态机。

协议操作：利用全序多播 (Totally ordered multicast) 将更新发送给所有副本，确保所有人收到的顺序一模一样。

基于团体 (Quorum-based)：

核心逻辑：利用数学公式保证冲突互斥（这就是你之前看到的那个算法）。

# 容错

## 基本概念

能够容错的系统就是可靠的系统，可依赖性（Depenable）的指标：

1.可用性：系统处于可工作状态的时间比例

在 [0, t) 时间段内，组件 C 可用的时间比例A=MTTF/MTBF

2.可靠性：系统能够持续无故障运行的能力（Reliable）

平均失效MTTF、平均恢复MTTR、两次失效平均时间MTBF=MTTF+MTTR

3.安全性：系统发生灾难性事故的概率极低（出故障也不会造成安全问题）

4.可维护性：系统故障后修复的难易程度

故障Fault->错误Error->失效Failure

故障：产生错误的根本原因

错误：可能导致失效的状态

失效：外部可见的异常

故障分类：

暂时故障：偶然发生一次，之后不会重复出现

间歇故障：反复且周期性地发生

持久故障：在被修复之前会一直存在的故障

失效模型/故障模式：

崩溃失效 (Crash failure)：服务器停止运行，但在停止前工作是正确的 。

遗漏失效 (Omission failure)：即不能响应消息（接收/发送消息失败）

定时失效 (Timing failure)：响应虽然正确，但超出规定的时间范围（快/慢）

响应失效 (Response failure)：

值失效：给出的结果数值错误 。

状态转换失效：偏离了正确的控制流逻辑 。

任意失效 (Arbitrary failure)：又称拜占庭失效 (Byzantine Failure)。服务器可能在任意时间产生任意响应，甚至是恶意欺骗 。

宏观失效分类：

遗漏性失效 (Omission)：该做的没做

执行性失效 (Commission)：不该做的做了

停机失效分类（从探测者/客户端视角）

当你作为一个客户端去观察一个可能坏掉的服务器时，你会感受到以下几种“停机”状态 ：

Fail-stop (故障-停止)：它挂了，而且你能肯定它挂了 。

Fail-noisy (故障-喧闹)：它挂了，你最终能肯定它挂了 。

Fail-silent (故障-静默)：它没动静，但你分不清它是真挂了还是网络丢包了 。

Fail-safe (故障-安全)：它出了任意错误，但这些错误是无害的 。

Fail-arbitrary (故障-任意)：它出了任意错误，且可能带有恶意行为

。

失效探测：

当一个系统停止响（Halting）时，探测者无法感知其任何行为（无法区分对方彻底宕机 (Crash) /网络拥塞致消息遗漏 (Omission) ）

同步系统和半同步系统可以检测崩溃失效

冗余掩盖故障：

1. 信息冗余：在数据单元中添加额外的位数据使错乱的位恢复正常 （纠错位）

2. 时间冗余：如果系统出错，一个动作可以再次执行(事务处理) （多次尝试）

3. 物理冗余：通过添加额外的装备或进程使系统作为一个整体来容忍部分组件的失效或故障。 （多配几套设备备用，几个设备一起计算或者进程一起计算）

## 进程容错/恢复

进程组特点：透明性（系统将多个进程放在一个组里，并将其作为一个单一的抽象进程来处理 。对客户端来说，它不知道也不关心组内有多少个副本，消息和交互都是面向“组”的）

组织结构：

平面分组：组内所有进程地位平等，决策通常通过广播和投票达成 。优点是没有单点故障，但管理较复杂。

层次化分组：有一个协调者负责管理，其他是工作者 。优点是效率高，但协调者挂了需要重新选举（对应之前的选举算法）。

K-容错组定义：该组最多可以屏蔽 K 个成员失效而依然能给出正确结果 。

场景1：停止失效 (崩溃/遗漏)

需求：K+1 个成员。

逻辑：只要有一个活着的，就能给出正确答案。

场景2：任意失效/拜占庭失效

需求：2K+1 个成员 。

逻辑：如果有 K 个进程失效且它们串通给出相同的错误结果，我们必须保证剩下K+1个正常进程占多数，这样客户端才能通过“相信多数”拿到正确值。

## 分布式共识（下一章详细讲具体的协议）

定义：故障情景，分布式共识使正常进程在有限步骤达成一致

要求：

1.一致性：正确进程输出值相同

2.有效性：输出的都是由某个进程提出的有效值

3.终止行：正确进程最终都有输出

分类：

A仅容忍“停止失效”：假设没有恶意的节点

B拜占庭容错：假设存在恶意节点

### 基于泛洪的共识（A类）

假设：同步系统、无恶意节点

步骤：

1.一轮开始，所有进程将自己的命令集发给其他所有进程

2.所有进程最后将收3.到的命令合并到自己的命令集

3.所有进程以相同的规则命令集中取出指令执行

（检查到失效的进程不做决定，再等一轮）

### Paxos共识（A类）

假设：可以是异步系统（更真实）、无恶意节点

核心角色：

1.Proposer：负责提出命令（共识）

2.Acceptor：负责决策共识，投票决定是否通过

3.Leaner：不参与决策，只学习最终结果

## 可靠C-S通信

### 可靠RPC

RPC调用过程，可能存在的故障：

1.找不到服务器

2.请求消息丢失

3.服务器宕机

4.应答消息丢失

5.客户端发送后宕机

服务器宕机解决办法（设计可靠RPC的方法）：

至少一次 (At-least-once)：客户端不断重试直到收到应答。这要求服务器的操作必须是幂等的 。

适用场景：纯读取操作、严格的写覆盖操作 。

至多一次 (At-most-once)：服务器端会记录请求序列号，如果发现是重复请求则直接丢弃，或超时即报错 。

适用场景：非幂等操作（如银行转账）。

刚好一次：这是理想状态，在逻辑上是不可能保证的

### 可靠多播

定义：一个消息能够可靠地发送到一个进程组G中，并且组G中的每个进程最终都能够接收到该消息 。

实现：在存在故障（消息丢失）的情况下，通过给消息编号，并基于编号缺失进行重发来保证可靠性。（类似TCP）

局限/问题：1.可扩展性差 2.消息缓存开销大 3.发送方可能被返回消息所淹没

## 分布式提交

定义：一个操作要么被进程组中的每一个成员执行，要么一个都不执行

### 两阶段提交协议（2PC）

阶段 1：表决阶段 (Voting Phase)

协调者 (Coordinator)：发送 VOTE-REQUEST 给所有参与者 。

参与者 (Participant)：返回 VOTE-COMMIT（同意）或 VOTE-ABORT（反对）。

阶段 2：执行阶段 (Decision Phase)

协调者收集选票。如果全票通过，发送 GLOBAL-COMMIT；只要有一票反对，发送 GLOBAL-ABORT。

参与者根据指令执行提交或回滚 。

协作者和参与者的状态机：

<img src="../../blog-assets/2026-08-08-distributed-systems-notes/image-011.png" alt="image 011" />
问题：节点失效时产生阻塞（可通过3PC解决）

失效后如何恢复：

参与者：

1.处于INIT：没有问题

2.处于READY：投了赞成票，但不知道后续指令。必须联系其他参与者

3.处于ABORT或COMMIT：幂等，只需重新执行一遍

协作者：

1.处于WAIT：重新发送REQUEST

2.处于COMMIT/ABORT：重发此决定，知道收到所有人的ACK

## 系统恢复

### 恢复的两种模式

1.前向恢复：不回头，调整进入下一个正确状态

前提：需要知道错误内容

2.后向恢复：撤销错误操作，回滚到上一个正确状态。

前提：需要记录历史状态（CheckPoint）

### 检查点机制（CheckPoint）/分布式快照（Snapshot）

恢复线路：最近一次的全局一致的检查点的集合

<img src="../../blog-assets/2026-08-08-distributed-systems-notes/image-012.png" alt="image 012" />
协调检查点：

所有进程在协调者的统一调度下，同时停下手头工作进行存档

独立检查点：

每个进程独立设置本地检查点

缺点：可能导致多米诺效应（依赖传递）

找恢复线路：不允许无源头被接受，但是允许丢包

### 消息日志

定期存档（检查点）的开销很大，我们可以通过“存档 + 记录操作日志”的方式，通过重放 (Replay) 来恢复状态。
