# 1. 概述

## 1.1 背景与概念

### 1.1.1 云计算定义

**定义**：云计算是一种通过网络，把共享的计算资源、存储资源、软件、平台等 IT 能力，以服务而非产品的形式提供给用户的计算模式，用户可以像使用公共设施一样，按需、弹性使用。它是分布式计算的一种特殊形式，能够远程提供可扩展、可测量的资源。

### 1.1.2 云计算公式

**公式**：云计算**=**数据 *****（软件**+**平台**+**基础设施）***** 服务

## 1.2 技术架构

### 1.2.1 技术架构层

1. **物理资源层**（基础设施）
物理资源：服务器、网络设备、存储系统等真实硬件资源。

2. **虚拟化资源层**（基础设施）
   把物理资源虚拟成虚拟机、容器、虚拟网络、虚拟存储，实现弹性分配。

3. **资源管理层**（平台）
   对物理资源和虚拟资源进行池化管理，包括监控、调度、资源分配。

4. **计算支撑层**（平台）
   位于应用和资源之间，提供分布式运行环境、微服务环境、MapReduce、分布式文件系统、分布式数据库等。

5. **应用服务层**（软件）
   面向用户提供云应用和服务管理，典型技术包括应用架构、多租户等。

### 1.2.2 技术架构的支持能力

**两个全局支撑能力**：**分布式协同与一致性**  **安全与隐私保护**

## 1.3 技术特性与风险挑战

### 1.3.1 云计算技术特性

1. **按需自助服务**
   用户可以自己申请服务器、存储等资源，不需要人工干预。
2. **广泛的网络访问**
   通过网络访问服务，手机、平板、笔记本、台式机都可以使用。
3. **资源池化与多租户**
   云平台将底层物理资源和虚拟资源集中形成资源池，通过虚拟化、调度和访问控制机制为不同租户动态分配资源。多个租户可以共享同一底层资源池，但在数据、权限、性能和资源视图上保持隔离，从而提高资源利用率并保证租户之间互不影响。
4. **快速弹性伸缩**
   资源可以快速增加或释放。对用户来说，资源看起来近似“无限”。
5. **服务可测量**
   资源使用可以计量，所以才能按量付费、监控和优化。

### 1.3.2 云计算的风险与挑战

1. **网络空间安全风险**
   用户把数据和资源放到外部云上，信任边界扩大，安全风险增加。

2. **运营管理控制风险**
   云用户对资源的控制弱于自建机房，还可能受到网络延迟、带宽波动影响。

3. **软件移植性问题**
   不同云厂商接口、环境、安全机制不同，迁移应用可能困难，也叫厂商锁定。

4. **跨地区法律风险**
   数据可能存储或处理在不同地区，涉及隐私、监管、合规问题。

## 1.4 服务与部署模型

### 1.4.1 服务交付模型

| 模型 | 中文           | 提供什么                           | 用户主要做什么               | 例子                     |
| ---- | -------------- | ---------------------------------- | ---------------------------- | ------------------------ |
| IaaS | 基础设施即服务 | 计算、存储、网络等基础资源         | 装系统、部署软件、管理环境   | AWS EC2、阿里云 ECS      |
| PaaS | 平台即服务     | 配置好的开发、测试、部署、运行环境 | 开发和部署应用（不需要前面） | Google App Engine、Azure |
| SaaS | 软件即服务     | 可直接使用的软件                   | 使用和配置软件（不需要前面） | Salesforce CRM、Gmail    |

控制能力：IasS>PasS>SasS

### 1.4.2 部署模型

1. **公有云 Public Cloud**
   面向公众或多个组织开放，由云服务商运营。
2. **私有云 Private Cloud**
   为单个组织使用，控制权更强，安全和合规性更好。
3. **社区云 Community Cloud**
   面向有共同需求的一组组织，比如政府、医疗、教育行业。
4. **混合云 Hybrid Cloud**
   多种云组合使用，比如核心数据放私有云，弹性业务放公有云。

## 1.5 SLA与QoS

**SLA：**是服务等级协议，描述云服务商承诺的服务质量QoS、保证和限制。

**QoS：**

1. **可用性 Availability**
   服务正常运行时间比例，比如 99.9%。

2. **可靠性 Reliability**
   服务在规定条件下不发生故障的概率，例如 MTBF 平均故障间隔时间。

3. **性能 Performance**
   包括带宽、吞吐量、响应时间、实例启动时间等。

4. **可扩展性 Scalability**
   系统最大可扩展能力，比如最多扩到多少台服务器、多少 GB 存储。

5. **弹性 Resiliency**
   系统从故障中恢复的能力，比如平均切换时间 MTSO、平均系统恢复时间 MTSR。




# 2. 基础算法与机制

## 2.1 分布式通信

**通信分类：**
瞬时vs持久
同步vs异步

**中间件：**

在应用层和OS之间添加消息中间件，作用屏蔽底层异构性，提供通用接口

### 2.1.1 消息队列

**一句话**：发送消息只需要把投递消息到消息队列，不需要双方同时在线（每个节点有自己的接受队列和发送队列）

**特点**：持久、异步

**重点机制：**

1. 消息寻址：消息发到哪个队列
2. 消息路由：消息怎么转发过去
3. 消息代理：负责格式转换、主题路由等

### 2.1.2 RPC/远程过程调用

**一句话**：允许调用其他机器上的远程过程，就像调用本地过程一样透明

**特点**：同步/异步

**关键问题：**

1. 参数封装 marshaling：讲参数转换为统一格式
2. 客户端和服务端绑定 binding

### 2.1.3 多播/广播

**广播** Broadcast：发给所有节点
**多播** Multicast：发给某一组节点

**多播方式：**

Overlay-based：将节点组织为树或者网格等拓扑结构（应用层逻辑组织），然后按照这个结构传递消息。
优：可控，无重复消息。缺：维护拓扑
Gossip-based：不依赖固定路径，以随机的方式将信息传播到网络中，在一定时间内使得系统内所有节点消息数据一致。
优：简单、鲁棒性、扩展性好 缺：重复消息

**Gossip-based三种基本范式 (P和Q之间的信息交换模式)**
Push (推)：节点 P 主动将更新推给随机节点 Q 。
Pull (拉)：节点 P 主动从随机节点 Q 拉取更新 。
Push-Pull (推拉结合)：双方互相交换，信息扩散效率最高

## 2.2 分布式同步

### 2.2.1 物理时钟同步

**概述**：需要精确时间+顺序，要进行物理时钟同步（因为会漂移）

**方法**：通过NTP协议与外部时钟UTC进行同步

### 2.2.2 逻辑时钟同步

**概述：**只需要事件发生顺序，则可以使用逻辑时钟

**Happens-before/因果关系 a->b，规则**：
1.进程内：如果a和b是同进程中两事件，并且 a在 b之前到达，则有：a->b
2.消息间：如果a是消息的发送事件，b是消息的接收事件，则a->b
3.传递性：如果 a->b 并且 b->c 则 a->c
4.并发关系：如果既不能证明 a→b，也不能证明 b→a，则称 a 和 b 是并发的

#### 2.2.2.1 Lamport逻辑时钟

**Lamport逻辑时钟算法**：
目标：为每个事件分配一个时间戳 C(e)，使得：如果 a→b，则 C(a)<C(b)
规则：暂时略

**应用：全序多播（使用Lamport逻辑时钟）**
暂时略

#### 2.2.2.2 向量时钟

**向量时钟算法**：
目标：为每个进程i分配一个向量VCi，VCi(i)是本地时钟，VCi(j)是i所认为的j的时钟，使得：a→b 等价于 ts(a)<ts(b)，即：

1. a向量的所有维度都 ≤b 向量
2. 至少有一个维度严格<

规则：暂时略

**应用：因果有序多播（使用向量时钟）**
暂时略

### 2.2.3 分布式互斥

**分类：**
基于许可：如果进程需要访问临界区或者访问资源，需要从其他进程获得许可。
	集中式（存在协调者）
	非集中式（存在多个协调者）
	分布式（不存在协调者）

基于令牌：仅有的一个令牌在进程之间传递。拥有令牌的进程可以访问临界区或者将令牌传递给其他进程。

#### 2.2.3.1 集中式（基于许可）

设置一个协作者Controller
**流程**：
请求：进程 P发送 REQUEST 给协作者
回复：如果临界区空闲，协调者回复 OK；如果被占用，协调者将请求放入队列，不回复。退出临界区，发送 RELEASE。协调者从队列取下一个进程发 OK。
**优点**：简单，每个进入/退出仅需 3 条消息
**缺点**：单点故障和性能瓶颈。

#### 2.2.3.2 非集中式（基于许可）

向N个协作者（均具有管理权）申请访问。获得m>N/2个协作者的OK，才可以访问。
**优点**：减少了单个协作者失效，造成的影响
**缺点**：协作者宕机后恢复，可能忘记发出去的许可，导致再度颁发许可互斥失效。

#### 2.2.3.3 分布式Ricart & Agrawala（基于许可）

**流程**：
请求：Pi想进入，向所有进程广播Request（包含资源、i、时间戳）
接收：
	1.若不在临界区且不想访问：回复OK（单播）
	2.已在临界区：不应答，放入队列
	3.不在临界区但想访问：比较时间戳
		接收到的时间戳更早，OK；
		自己的更早，放入队列
退出：向等待队列发送OK

**缺点**：单个故障点被n个故障点所取代， 故障概率高。进程维护开销较大，每次需要2(n-1)个消息。同时网络流量大大增加。

#### 2.2.3.4 令牌环算法（基于令牌）

将进程组织成逻辑环（每个进程知道下游），令牌在这些进程之间传递。拥有令牌的进程进入临界区。

### 2.2.4 分布式选举

**背景**：解决如何选择协作者的问题（有协作者的算法的前置条件）
**假设**：
	1.所有进程有唯一ID
	2.所有的进程都知道系统中的其他进程ID，但不知道是否运行
	3.选举算法就是要找到具有最大ID的运行的进程

#### 2.2.4.1 Bully算法

**触发条件**：任何进程 P 发现协调者不再响应。
**算法流程**：

1.P 向所有 ID 比自己大 的进程发送 ELECTION 消息。
2.如果有更高 ID 的进程回应 OK（表示它还活着），则 P 的任务结束，等待更高 ID 的进程去完成选举。
3.如果没有进程回应，说明 P 是当前活着的最高 ID 进程。
4.P 赢得选举，向所有进程广播 COORDINATOR 消息。

#### 2.2.4.2 Ring算法

**逻辑结构**：进程按 ID 大小排列在一个逻辑环中，Pi的下游是 Pi+1
**算法流程**：
发现故障的进程P创建一个包含自己ID的ELECTION消息，传给下游（若下游挂了，则传给下下游，类推）
传递：每个进程收到消息后，将自己的ID添加到列表里，继续向下游传。
确定：消息绕环一圈回到发起者 P。P 查看列表，选出ID最大的进程。
通知：P发送COORDINATOR消息再绕一圈，通知所有人“谁是新领袖”以及在环中的节点

## 2.3 数据副本与一致性

### 2.3.1 数据副本

目的：可靠性 可扩展性

### 2.3.2 一致性

#### 2.3.2.1 一致性模型

数据为中心的一致性：连续一致性、因果一致性

客户为中心的一致性：最终一致性（弱一致性）

##### 2.3.2.1.1 连续一致性

所有进程必须看到完全一致的全局操作顺序（通过读看到）；每个进程内部，该进程所执行的所有操作在全局序列中出现的顺序不变

##### 2.3.2.1.2 因果一致性

有因果关系的写操作，所有进程必须以相同顺序看到；没有因果关系的并发写操作，可以被不同进程以不同顺序看到。

##### 2.3.2.1.3 最终一致性

如果之后没有新的更新操作，经过一段时间后，所有副本最终会收敛到相同状态。

判定准则：

1.单调读
读取同一个值，只能是越来越新（不能读到旧数据）
2.单调写
写入同一个值，必须等上一次写操作完毕，才能执行新的写。
3.读写一致性
写后读同一数据，立即看到更新
4.写读一致性
读后写，保证写发生在所读值上。

#### 2.3.2.2 一致性协议

##### 2.3.2.2.1 主副本协议

思想：一个副本作为主副本，所有写操作先交给主副本处理，再由主副本传播到其他副本。

分类：

Remote-write：写操作转发到远程主副本执行
Local-write：主副本可以迁移到当前写入位置

##### 2.3.2.2.2 全复制写协议

思想：去中心化，写操作发给所有副本。

##### 2.3.2.2.3 多数派协议Quorum

N：副本总数
R：读操作需要访问的副本数
W：写操作需要访问的副本数

R + W > N
W > N/2

## 2.4 进程失效与分布式共识

### 2.4.1 失效

细分类：
崩溃失效、遗漏失效、时序失效、任意失效/拜占庭失效

考试抓主线：
停止失效：节点故障
拜占庭失效：节点可能发松恶意消息

### 2.4.2 分布式共识

**定义**：故障情景，分布式共识使正常进程在有限步骤对某个值达成一致

**要求**：
1.一致性：正确进程输出值相同
2.有效性：输出的都是由某个进程提出的有效值
3.终止行：正确进程最终都有输出

**分类**：
A 只处理停止失效：假设没有恶意的节点（Paxos协议）
B 可处理拜占庭失效：假设存在恶意节点

**Paxos协议：**

角色：

Proposer：提出提案值
Acceptor：接受或拒绝提案
Learner：学习最终被选定的值

过程：

第一阶段：Prepare / Promise先申请编号，获得多数承诺。
第二阶段：Accept / Accepted再提交值，获得多数接受。

**拜占庭容错：**要容忍 k 个拜占庭故障节点，通常至少需要 3k + 1 个节点

### 2.4.3 分布式提交 - 两阶段提交2PC

目标：一个操作要么被进程组中的每一个成员执行，要么一个都不执行

**第一阶段：投票阶段**
协调者询问所有参与者是否可以提交。
参与者返回 Yes 或 No。
**第二阶段：决定阶段**
如果所有参与者都 Yes，协调者发送 Commit。
只要有一个 No，协调者发送 Abort。

3PC增加预提交阶段，解决2PC的阻塞问题。

## 2.5 系统恢复

### 2.5.1 两种恢复模式

前向恢复：不回头，调整进入下一个正确状态

   前提：需要知道错误内容

后向恢复：撤销错误操作，回滚到上一个正确状态。

   前提：需要记录历史状态（CheckPoint）

### 2.5.2 检查点

检查点：分布式系统的状态记录，即分布式快照

恢复线路：最近一次全局一致的检查点集合

协调检查点：所有进程在协调者的统一调度下，同时停下手头工作进行存档

独立检查点：每个进程独立设置本地检查点，缺点：可能导致多米诺效应（依赖传递）

# 3. 虚拟化技术

## 3.1 虚拟化技术

### 3.1.1 概念

**定义**：虚拟化就是把物理 IT 资源（服务器、存储设备、网络、电源）抽象成虚拟 IT 资源，让多个用户或多个系统共享同一批硬件，但彼此隔离。

**优点：**

1. 硬件无关性：虚拟机不强依赖具体物理硬件
2. 服务器整合：一台物理机运行多个虚拟机，提高资源利用率
3. 资源复制：虚拟机可迁移、复制、快照，因为状态可保存为文件

**虚拟机VM：**将服务器物理机虚拟化，得到虚拟机。包括Guest OS和应用。

### 3.1.2 VM架构

| 架构                | 中文       | 结构                         | 特点                     | 适用场景           |
| ------------------- | ---------- | ---------------------------- | ------------------------ | ------------------ |
| Hosted / Type II    | 寄生架构   | 硬件 -> 宿主 OS -> VMM -> VM | 方便、功能丰富，性能较低 | 桌面系统、个人开发 |
| Bare-metal / Type I | 裸金属架构 | 硬件 -> VMM/Hypervisor -> VM | 性能高、安全性高         | 服务器、云数据中心 |

### 3.1.3 虚拟机技术分类

#### 3.1.3.1 硬件仿真

**架构**：Hosted

**思想**：VMM用软件模拟全套硬件，VM陷入VMM中，由VMM模拟执行

**优点：**GOS不需要修改

**缺点：**非常慢

#### 3.1.3.2 全虚拟化

**架构：**Hosted/Bare-Metal

**思想：**GOS不修改，VMM 在GOS和硬件间捕获并处理敏感特权指令

**优点：**GOS不用修改

**缺点：**较慢

#### 3.1.3.3 半虚拟化

**架构：**Bare-Metal

**思想：**修改GOS，以配合VMM。执行特权指令时，给VMM发送Hypercall，支持批处理和异步（所以速度快）

**优点：**速度较快

**缺点：**GOS进行修改，用户体验差

#### 3.1.3.4 硬件辅助虚拟化

**架构：**Hosted/Bare-Metal

**思想：**硬件支持虚拟化。VMM 运行在 Root 模式，Guest OS 运行在 Non-Root 模式，Guest 执行特殊指令时切换到 VMM 处理。

**优点：**速度最快

**缺点：**硬件实现不够优化

### 3.1.4 CPU虚拟化

**核心问题：**特权/敏感指令执行

**技术（刚刚的具体实现）：**

全虚拟化：优先级压缩（GOS和VMM运行在不同Ring），VMM捕获特权指令后模拟执行 + 二进制翻译：扫描GOS难虚拟化的指令，翻译成可虚拟化指令
半虚拟化：Guest OS 主动发 Hypercall（超级调用）
硬件辅助：VT-x/AMD-V 提供新模式支持

### 3.1.5 内存虚拟化

**目标：**让每个虚拟机都以为自己拥有完整连续的内存空间，同时保证虚拟机之间隔离。

**技术：**

全虚拟化：VMM为Guest维护影子页表，将Guest虚拟地址映射为Host物理地址，透明

硬件辅助：扩展列表

### 3.1.6 I/O虚拟化

**目标：**不仅让虚拟机访问到它们所需要的I/O资源，而且要做好它们之间的隔离工作，更重要的是，减轻由于虚拟化所带来的开销。

**技术：**

全虚拟化：VM->陷入->VMM->VMM处理

半虚拟化 （ V i r t i o）：通过前端（安装在Guest）/后端（安装在特权域）架构，将Guest的I/O请求传递到特权域，缩短了路径

## 3.2 容器虚拟化

**概述：**容器本质是自带环境的进程，共用一个操作系统，通过命名空间和进程组来实现隔离性

**优点：**

1. 轻量、开销小、启动快（ms）
2. 数量多（每个主机可以支撑上万个）
3. 自带环境，方便打包部署

**缺点：**

1. 隔离性、安全性较差
2. 不能随意修改操作系统内核

**三大技术：**

1. Namespace

   实现视图隔离，即容器只能看到自己的进程。

2. Cgroups

   实现资源隔离，即容器只能使用限制的资源。

3. Rootfs

   实现文件系统隔离，即提供容器的文件系统/容器镜像，但不包含内核

## 3.3 网络虚拟化

**概述：**把物理网络**设备**和网络**功能**抽象成软件可管理的**逻辑**网络。

**方式：**

1. 桥接 Bridge
2. NAT
3. 虚拟交换机
4. 分布式虚拟交换机

# 6. 云存储与文件系统

## 6.1 网络存储系统

**存储系统分类**：

集中式存储：专门的存储节点，用 RAID 保证数据安全
	SAN：聚合不同存储设备
	NAS：聚合不同文件系统

分布式存储：多台服务器的硬盘整合成统一存储资源，用副本或纠删码保证可靠性

### 6.1.1 SAN

SAN 是 Storage Area Network，存储区域网络。

**特点**：

1. 访问方式：提供块级别访问
2. 连接方式：通过专门网络连接（如iSCSI和FC）
3. 性能：性能高、延迟低

4. 场景：常用于数据库、虚拟化、OLTP 等场景，服务器像访问本地磁盘一样访问。

再分类：

IP SAN：基于 TCP/IP，典型协议 iSCSI
FC SAN：基于光纤通道 FC，性能更高，成本更高

### 6.1.2 NAS

NAS 是 Network Attached Storage，网络附加存储。

**特点**：

1. 提供文件级别访问
2. 通过 NFS、CIFS 等协议（都是以太网连接）共享文件
3. 性能：性能低
4. 场景：使用简单，适合文件共享、备份、归档

## 6.2 分布式文件系统

传统分布式文件系统：NFS、CIFS
现代分布式文件系统：GFS、HDFS、Ceph

### 6.2.1 HDFS

#### 6.2.1.1 概述

**概述**：HDFS 是 Hadoop Distributed File System，可以理解为 Google GFS 的开源实现。

**特点**：

1. 容量大，支持单个大文件
2. 高可靠、高扩展、快速访问
3. 为 MapReduce 设计

**适用场景**：

1. 大文件顺序读
2. 一次写入，多次读取
3. 批处理分析

#### 6.2.1.2 架构

**Matser-Slave架构**：
NameNode：名称节点，存储元数据
DataNode：数据节点，真正存储数据块

#### 6.2.1.3 NameNode

**NameNode的元数据**：
FsImage：某一时刻完整的文件系统元数据快照
EditLog：从快照之后发生的修改操作日志

**NameNode启动后**：
先加载 FsImage
再执行 EditLog
生成新的 FsImage
清空 EditLog

#### 6.2.1.4 Secondary NameNode

**作用**：

1. 保存元数据备份
2. 帮助合并，加速启动：下载 FsImage 和 EditLog，合并成新的 FsImage，再传回 NameNode

#### 6.2.1.5 数据块放置策略

**默认 3 副本**：
第 1 份：本地节点
第 2 份：同机架其他节点
第 3 份：不同机架节点
更多副本：随机放置

#### 6.2.1.6 Client写入过程

1. Client 从 NameNode 获取 DataNode 列表
2. Client 写第一个 DataNode
3. 第一个 DataNode 转发给第二个
4. 第二个再转发给第三个
5. 所有副本写完后返回确认

#### 6.2.1.7 Client读过程

1. Client 向 NameNode 查询文件 Block 位置
2. NameNode 返回每个 Block 所在 DataNode
3. Client 选择距离近的 DataNode 读取
4. Client 直接从 DataNode 读取数据

### 6.2.2 Ceph

**概述：**Ceph 是一种大规模、无单点故障、去中心化的分布式存储系统。

**提供接口类型：**对象存储、块存储和文件存储（即不止支持文件存储）

Chord通过指纹表加速查找

# 7. 分布式数据库

## 7.0 NoSQL

**是什么：**No-SQL 或 Not Only SQL，非关系型数据库

**优点：**

1. 多节点复制和分区存储，无单点故障
2. 水平扩展：加机器就能扩容
3. 低成本部署
4. 适合高并发写入
5. 批量高速访问：适合数据分析和扫描

**缺点：**

1. 不支持复杂关系操作
2. 没有统一SQL查询语言
3. 一致性保证较弱，采用BASE模型（最终一致）
4. 和传统 SQL 应用集成不方便

**分类:**

1. 键值数据库 Key-Value
2. 列族数据库 Column Family / Wide Column
3. 文档型数据库 Document
4. 图数据库 Graph

## 7.1 键值数据库

数据模型：key -> value

代表：DynamoDB、Redis、Scalaris、Memcached、Dynamo、Voldemort

优点：速度快、模型简单、容易水平扩展、容错性好、适合最终一致性

缺点：不擅长表达复杂对象关系、复杂查询能力弱

## 7.2 列族数据库

数据模型：RowKey -> Column Family -> Column -> Value，按列族存储数据

代表：BigTable、HBase、Cassandra、Hypertable、PNUTS

特点：一个列族中的列物理上相邻、适合按列访问、适合稀疏数据、适合大规模扫描和分析

## 7.3 文档型数据库

数据模型：documentId -> document

代表系统：MongoDB、CouchDB、Couchbase

文档类型：JSON、BSON、XML、半结构化数据

优点：结构灵活、适合复杂对象、不需要预先定义固定表结构、天然支持嵌套对象

缺点：复杂查询和统一查询语法不如 SQL 成熟

## 7.4 图数据库

数据模型：G = (V, E)

代表系统：Neo4j、FlockDB、Pregel、InfoGrid、HugeGraph、JanusGraph



# 8. 分布式并行计算框架

传统并行：计算复杂，节点之间协作紧密。
大数据并行：数据巨大，把数据切开，各节点独立处理，再汇总。
**本章为后者**

## 8.1 大数据并行计算模式 - MapReduce

**概述**：MapReduce 是一种大规模数据集并行处理的编程模型，把一个大任务拆成很多小任务并行处理，最后再把结果汇总。

**流程：**Input -> Split -> RecordReader -> **Map** -> Shuffle & Sort -> **Reduce** -> Output

**InputSplits**：将Input大数据划分为若干个小任务数据

**RecordReader：**将数据转换为键值对

**Map：**接受键值对输入，输出键值对

**Shuffle & Sort** ：Shuffle负责按Key分区，传输到对应的Reduce；Sort 对一个Reduce上的Key进行排序

**Reduce：**对该Reduce上的键值对做聚合运算

## 8.2 大数据并行计算框架

概述 特点 组件/概念 场景

### 8.2.1 Hadoop MapReduce

**概述**：Apache 下的大数据分布式存储和计算框架。

**核心组件**：
HDFS：分布式文件系统
MapReduce：分布式并行计算模型
YARN：资源管理和任务调度

**适合**：离线批处理（慢）

### 8.2.2 Spark

**概述**：基于**内存**计算的大数据并行计算框架。

**特点：**

Spark 支持内存计算，效率更高
Spark 也属于 MapReduce 思想
Spark 操作类型更多，编程模型更灵活
Spark 基于 DAG 调度，任务优化能力更强

**RDD**：弹性分布式数据集，是Spark的核心数据抽象

**RDD两类操作：**

Transformation：转换操作，如 map、filter、join，惰性执行
Action：动作操作，如 count、collect、saveAsTextFile，触发真正计算

**RDD特点：**

分布式：数据分布在多个节点上
只读不可变：转换操作会生成新的 RDD
可分区：每个 RDD 由多个分区组成
可容错：通过 lineage 依赖关系重新计算丢失分区

**RDD依赖关系：**

窄依赖：一个父分区只对应一个子分区，可流水线执行，效率高
宽依赖：一个父分区对应多个子分区，需要 shuffle，开销大

**适合场景：**快速批处理、迭代计算、机器学习

### 8.2.3 Storm

**概述：**Storm 是实时流计算框架，用来处理持续不断到来的数据流。

**核心概念：**

Tuple：一条数据
Stream：连续不断的 Tuple
Spout：数据源
Bolt：处理节点
Topology：整个处理流程图

**组件：**

Nimbus 分配任务
Supervisor 执行任务
ZooKeeper 负责协调和容错

**适合场景：**实时流处理







# 9. 云计算应用

## 9.1 应用程序架构技术

### 9.1.1 SOA

**概述：**面向服务架构，把应用拆成多个服务/功能单元，每个服务通过接口和契约进行交互。

**SOA 三种角色：**

```
服务提供者 Service Provider
服务请求者 Service Requester / Consumer
服务代理 Service Registry / Broker
```

**SOA 一个媒介：**

```
服务总线 Service Bus
```

**SOA 三个操作：**

```
发布 Publish
查找 Discover
绑定 Bind
```

服务提供者把服务发布到注册中心
服务请求者去注册中心查找服务
找到后绑定并调用服务

**实现：**

Web Services：WSDL + SOAP + UDDI
RESTful HTTP
Messaging：ActiveMQ、JMS、RabbitMQ
Apache Thrift

### 9.1.2 微服务架构

**概述：**微服务是把传统单体应用按功能、数据等切分成多个小服务。

**特点**：1.每个服务规模小 2.服务之间轻量级 3.通信服务可以独立部署、运行、扩展

**优点（相对SOA）：**

1. 持续交付和持续部署更容易
2. 易维护、易调试
3. 可以独立扩展
4. 故障隔离性好
5. 容易复用已有功能

**微服务与容器：**容器是承载微服务的理想平台，每个微服务可以打包成 Docker 镜像，容器云可以简化创建、集成、部署和运维

### 9.1.3 Serveless无服务器架构

**概述：**用户无须关注支撑应用服务运行的底层主机，软件的运行环境是支持Serverless的云计算平台，只需编写函数

**核心技术：**

FaaS：Function as a Service，函数即服务
BaaS：Backend as a Service，后台即服务

**特点：**

按需加载
事件驱动
状态非本地持久化
非会话保持
自动弹性伸缩
应用函数化
依赖服务化

**局限：**

控制力：用户对底层资源控制力弱
可移植性：依赖特定平台，迁移困难
安全性：函数间隔离性和安全性可能较弱
性能：冷启动带来延迟
执行市场：不适合长时间持续运行任务
成熟度：技术生态还在演进

**Serverless vs 微服务：**

相同点：都强调功能拆分，最小单元专注做一件事。

不同点：
Serverless 最小单位是函数，强调减轻服务器管理负担。
微服务最小单位是服务，强调应用架构灵活性。



Serverless 适合短时、无状态、事件驱动、弹性波动大的任务；
不适合长时间运行、强状态、低延迟、强控制需求的任务。

## 9.2 多租户技术

**定义：**多个用户或组织共享同一套系统或程序组件，同时保证数据和操作隔离。

**作用：**提高资源利用率、提高服务能力、增强弹性、降低运维成本

**多租户成熟度模型：**

I型：定制实例
每个租户有自己的程序版本和实例。

II型：可配置
同一程序，不同租户通过配置使用不同实例。

III型：多租户
多个租户共享同一个应用实例，隔离界面和数据。

IV型：可扩展
通过多层架构动态调整服务器，适应负载变化。

**特点：**

使用隔离：一个租户不能影响其他租户性能
数据安全：租户不能访问其他租户数据
可恢复性：每个租户可独立备份和恢复
应用升级：共享组件升级不应影响租户
可扩展性：随租户数量和负载增长扩展
使用计费：按实际使用计费
数据层隔离：数据库、表、Schema 隔离

**实现层次：**

基础设施层：共享硬件和操作系统
中间件层：共享中间件
应用层：共享应用，由应用逻辑隔离租户
数据层：数据库、Schema、表隔离

**数据存储：**

独立数据库
共享数据库 + 独立 Schema
共享数据库 + 共享 Schema
