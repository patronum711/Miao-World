# 1 基于Redis Hash + Token实现分布式Session，采用刷新拦截器+验证拦截器验证登陆

## 1.1 实现过程

### **1.1.1 登录板块**

客户端请求验证码，过程：

1. 客户端输入电话号码，作为参数发送请求
2. 服务器接收，查验号码合法性
3. 服务器生成Code验证码，存储到Redis中（Key中加入Phone作为标识）
4. 服务器将Code发送给客户端（短信）

客户端输入验证码登录，过程：

1. 客户端携带Code和手机号发送
2. 服务器接收手机号和Code，验证手机号合法性
3. 根据手机号查验Redis中是否存在Code字段，并核对是否一致，如果存在且一致，通过验证
4. 验证通过后，立即删除Redis中的验证码
5. 通过手机号查询用户，如果不存在该用户则注册（创建用户信息，并添加到数据库）

// 到此“登录”本身就成功了，但还需要保存用户信息到Redis(Session)中

1. 生成一个UUID token，用作Redis中Session的标识（稍后返回给用户，用户此后访问会在请求请求头携带此token）
2. 将用户信息写入Redis中的Session，Key中包含token标识，设定一段时间的有效期

// 限流

请求验证码，使用限流（粒度为PARAM：手机号），同一手机号每分钟只能发送1次请求。

### 1.1.2 验证登录板块（拦截器）

刷新拦截器（全部放行），优先级0，拦截路径为全部：

1. 获取请求头中的token
2. 根据token查询Redis中的用户信息，查不到就直接放行
3. 如果查得到将查找结果放入ThreadLocal，直接放行
5. 刷新session的过期时间

登录验证拦截器，优先级1，拦截路径为需要登录验证保护的路径：

1. 查看ThreadLocal中的用户信息是否存在
2. 如果存在才放行，不存在返回401

拦截器的 `afterCompletion`执行：

ThreadLocal.remove()

### 1.1.3 登出板块

1. 从请求头获取token
2. 删除Redis中对应的Session数据（`login:token:{token}`）
3. 清除ThreadLocal中的用户信息

## 1.2 问题拷打

**1.为何使用Redis替代Session，而不使用Session**

Session是每台服务器单独存储的，在服务器集群的环境下：客户端被分配到服务器A，并成功登录，存储了Session在服务器端A，下一次访问被分配到服务器B，进行登录验证，B就找不到这个Session

而Redis（讲好处）是在多服务器间共享的，并且也是Key-Value的形式，并且数据存储在内存中

**2.使用Redis的好处**

数据存储在内存，访问读写快；在服务器集群的环境中是共享的；是Key-Value的形式；支持过期

**3.为什么要使用Token做为Key**

Redis在多服务器之间虽然是共享的，但我们需要用Token作为Key，来标识区别不同用户的数据。Token就相当于一个每个用户独有的SessionID，每个用户通过自己的Token获取到自己的用户信息。

**4.为什么要使用两个拦截器，刷新拦截器作用**

如果只使用一个拦截器，拦截器中有一个步骤是对Redis中的用户信息进行刷新，拦截路径就只拦截需要登录验证保护的路径，而如果用户访问不需要登录验证的板块，就不会被拦截，也就无法进行刷新，这是不合理的。因此采用两个拦截器，一个拦截器进行刷新工作，并提前去根据token获取用户信息，将结果存入ThreadLocal，登录拦截器就只需要查看ThreadLocal中是否存在用户信息结果。

**5.为什么刷新拦截器后面要移除ThreadLocal中的用户信息**

ThreadLocal是绑定在线程上的，线程可能会复用给下一个请求，导致用户信息串用；

ThreadLocal内存泄漏的问题

**6.为什么要将用户信息存入ThreadLocal/作用**

保证线程内数据一致性：在同一个请求处理过程中，用户信息不会发生变化，放在ThreadLocal中可以确保整个请求链路中获取到的都是同一份数据。

线程隔离安全：每个请求有自己的线程，ThreadLocal天然提供了线程隔离，不会发生数据串用。

方便API设计：业务代码可以直接从ThreadLocal获取用户信息，而不需要在每个方法参数中传递用户对象

避免重复查询Redis，提高性能：一次请求中，用户信息可能在多地方被使用（如登录拦截器、业务逻辑、权限校验等），减少Redis压力

**7.Redis的Key的设计**

业务:子业务:标识（例如id/token）

**8.用户登录状态（Session）过期时间如何设定**

根据业务情况具体判断，大体上：

Web端，30min-2小时

移动端，可以长达十几天，因为移动端是个人专属设备，手机本身也有密码；用户使用更方便

**9.用户登录状态（Session）存了哪些数据？**

非敏感、频繁使用数据，比如id、昵称、 头像等

**10.用户数量很大，Redis内存不够如何？**

**内存优化：**精简Session数据，只存必要字段；合理设置过期时间，活跃用户延长，不活跃用户缩短
**架构优化：**分片存储：按用户ID分到不同Redis实例；冷热分离：活跃用户存Redis，不活跃用户存数据库/不存；

**11.验证码登录成功后为什么要立即删除验证码？**

防止验证码被重复使用。

**12.验证码接口为什么需要限流？怎么实现的？**

验证码接口（`/user/code`）不需要登录就能访问，如果不做限流，恶意用户可以无限刷短信验证码，导致短信费用暴涨。

**13.方案选择：token为什么不用cookie传递？为什么不用JWT令牌？**

cookie可以被禁用，移动端不支持；

JWT也可以，无状态，自包含，但是JWT令牌服务端不可控，无法主动下线，只能等JWT令牌自己过期（过期时间也是在JWT令牌中的payload），颁布后就无法控制。

**14.Session里面存的是什么？**

用户非敏感信息，比如id、昵称、头像等

**17.一个用户能不能同时登录多个设备？**
有两种设计：
多端共存
每次登录生成一个新的 token，Redis 中每个 token 对应一个 Session，互不影响。
单端登录
可以额外维护 userId -> token 映射。新登录时先找到旧 token 并删除，再写入新 token。

# 2 Redis作数据缓存：旁路缓存+延时双删解决缓存不一致问题，缓存空值解决缓存穿透问题，设置互斥锁和逻辑过期解决缓存雪崩和缓存击穿问题，缓存预热

## 2.1 实现过程

在应用层和数据库之间引入了Redis作为缓存。这里我实际是做了两套缓存方案，最后根据实际情况选择了其中一种，

### 2.1.1 方案一：旁路缓存Cache Aside+延时双删解决，配合缓存空值解决缓存穿透

**查询：**

1.首先查询Redis缓存，如果缓存有数据，则直接返回数据

2.如果缓存没有数据，则查询数据库

3.如果查询到了数据，则写入缓存

4.最后返回查询结果

**更新：更新商店数据（延时双删）**

1.第一次删除Redis中的缓存

2.更新数据库

3.创建后台线程，延迟一段时间后，第二次删除Redis中的缓存

**配合缓存空值：**

对空值同样设置缓存，即Key+空值Value，这样查询空值就不会穿透到数据库

**场景：**

需要保证强一致性

### 2.1.2 方案二： 逻辑过期+互斥锁+异步重构解决缓存击穿问题

场景：某些促销活动前，已经提前预判热点数据。

逻辑过期：Redis缓存不设置过期时间，而是将过期时间作为一个字段设置在Value值中。保证缓存物理上一定存在。在活动开始前的时候，要进行预热，提前将所有数据加载进缓存（唯一数据来源）。最后统一进行删除。

**查询：**

1.先读缓存，缓存不存在，直接返回空；

2.如果缓存在，没过期，返回数据；

3.如果缓存在，且过期，尝试获取互斥锁，获取成功，开启后台线程来访问数据库+重构缓存，此线程返回旧值

4.如果缓存在，且过期，尝试获取互斥锁，获取失败，直接返回旧值。

**更新：**

更新数据库，同时更新缓存

**插入：**

更新数据库，同时更新缓存

**场景：**

更适合热点数据，要保证高可用性，保证请求一定不会打到数据库，但是可以容忍一定的数据不一致。

## 2.2 问题拷打

**1.什么是缓存不一致？解决缓存不一致有哪些方案？为何采用Cache Aside**

**缓存不一致：**Redis缓存中的数据与数据库中的数据不一致

**解决方案：**见八股

**为何采用Cache Aside：**

更常见，实现也简单。商品数据是典型的读多写少的数据，缓存命中率高

**2.解决缓存穿透有哪些方案？**

(1)缓存空值

(2)布隆过滤器：在应用层和缓存层添加布隆过滤器，原理详见八股

(3)在API入口做好参数的合法性检验

**3.解决缓存雪崩和缓存穿透有哪些方案？评价优缺点**

针对缓存雪崩：为缓存过期时间添加一个随机值，避免大量缓存同时失效

针对两者通用：

(1) 采用互斥锁+阻塞等待：对数据库访问添加锁，保证同时只有一个线程访问数据库

(2) 采用互斥锁+逻辑过期+异步重构：Redis缓存不设置过期时间，而是在Value值中增加过期时间字段；采用异步重构，首先探测到逻辑失效的线程，开启新线程进行缓存重构（查询数据库+写入缓存），自己则直接返回过期值，其他并发线程获取锁失败也直接返回过期值。

前者方案数据一致性好，但线程存在等待；后者方案存在短暂的数据不一致（返回逻辑过期的值），但是线程响应快，不存在阻塞等待。

**4.逻辑过期的具体实现？**

设置缓存时：将原Value和一个失效时间字段封装成一个新的对象作为Value，失效时间为失效的时间戳

读取缓存时：解析Value中的失效时间字段，比较当前时间和失效的时间，便可知道是否已经过期

**5.互斥锁的具体实现？**

采用Redis实现互斥锁，获取锁使用SetIfAbsent，释放锁则Delete

**6.为什么要引入逻辑过期？**

不采用逻辑过期而是实际过期的话，某线程发现过期，获得锁开始重构期间，其他线程由于缓存数据已被删除，只能等待缓存重构；而引入逻辑过期，其他线程也能获取到过期数据，直接返回，避免了等待，当然代价是可能存在数据不一致。

**7.为什么要延时双删**

解决传统方案“更新数据库-删除缓存”的小概率不一致问题：A线程读，不存在，读数据库旧值，B线程更新数据库为新值，删除缓存（删了寂寞），A线程写入缓存旧值。

新方案：第一次删除，保证尽快让旧数据失效，第二次删除，兜底清除更新期间其他线程可能写的脏数据旧值

延时原因：要让可能读到旧值的线程完成读旧值-写缓存这个完整过程。

**8.延时双删一定能保证一致性吗？**

仍然不能。极端情况概率还是有的，比如第二次删除失败了。

**9.延时双删，延迟时间？**

延时时间：略大于一次读数据库+写缓存的时间

**10.热点数据采用逻辑过期，数据越来越多，如何处理？**

1.分场景来看，如果是当前项目场景：

我这里的场景是，某些大型活动前，我们已知某些商品将成为热点数据，在活动开始前，将商品数据预热进缓存，数据的来源只有预热。也就是说如果去Redis查询数据，发现为空，就直接认为该数据没有参加活动，返回空值，不会去查询数据库加载数据，所以不存在数据越来越多的情况，活动结束后，统一数据删除即可。

2.那如果说，查询为空，要去加载数据，可以采用以下方式：

Redis设置一个热点集合SortedSet，每次访问业务数据本身时，在热点集合中添加该key+当前时间戳。设置后台定时任务，每隔一段时间就去扫描热点集合，找出一段时间内没有被访问的数据，清理数据本身以及将其从热点数据中移除。

# 4 乐观锁解决秒杀场景超卖问题

## 4.1 实现过程

超卖问题：购买秒杀优惠券有一个关键的部分是“查询”+“扣减”：查询优惠券库存数量，如果数量大于等于1，则扣减库存。这两个操作不是原子性的。如果不使用乐观锁，可能存在并发问题，假如库存刚好程都扣减库存，导致超卖。

1. 查询库存数量，若小于1，则购买失败
2. 扣除库存数量时，同时检查库存数量是否大于0，大于0时才能成功扣除

## 4.2 问题拷打

**1.这里如何体现乐观锁？**

乐观锁的思想是，不对资源提前进行加锁，而是直接尝试修改。我的项目这里运用到了类似于版本号机制的实现，在扣减库存数量时，增加条件判断，库存数量是否大于0.

**2.为什么要使用乐观锁而不使用其他悲观锁如Synchronized？**

加悲观锁导致该环节同时只有一个线程可以执行，其他并发线程则会阻塞，效率太低，造成性能瓶颈。这是一个典型的读多写少的场景，为了提高并发性能，所以选择乐观锁实现。

**3.这个方案存在“ABA”问题吗？在当前场景下需要处理吗？**

ABA问题是指一个值从A变成B，又变回A，乐观锁的版本号检查会认为没有变化。在纯扣减库存的场景下，库存数量只会单调递减，不会增加，所以不存在ABA问题。如果库存有“补货”操作，就需要关注。通用的做法是使用始终递增的版本号（version） 或时间戳来避免。

**4. 如果更新失败了，你直接返回失败。有没有更好的处理方式？**

当前场景下，失败通常意味着真没库存了，重试成功概率低，所以直接失败是合理设计。不过也有其他处理方式，可以引入有限次数的重试机制。例如，在扣减库存失败后，可以快速重试1-2次（再次重新查询库存，执行UPDATE）。重试前最好有短暂的随机延迟（如Thread.sleep(随机几十毫秒)），打散并发请求。

**5.乐观锁在极高并发下，大量请求更新同一行数据，导致大量失败，会不会有问题？**
会。这就是乐观锁的缺点——在高冲突场景下，大量失败重试会浪费资源（CPU、数据库连接）。

# 5 Redisson作分布式锁，解决秒杀场景一人多单问题

## 5.1 实现过程

我先讲一下秒杀下单整个过程吧，Redisson作分布式锁是其中的一个环节。（然后讲6.1）

## 5.2 问题拷打

**1.锁的粒度？**

锁对象可以设置为用户id+优惠券ID。这样保证了同一用户id购买同一优惠券的请求线程获取到的是一把锁，而不同用户id线程之间拿到的是不同的锁，是可以同时并发访问，因为不会导致一人多单问题。

**2.锁的范围？**

范围包括：检查是否已经下单+扣减库存+创建订单。

事务是在扣减库存和创建订单，锁一定要包括整个事务的开启和提交过程。如果锁先释放，再提交事务，锁释放的时候另一个线程得到了锁，可能读到数据库未提交的数据（脏读），比如认为用户还未下单，可能导致一人多单问题。

**3.当前场景获取锁失败的策略是？为什么**

直接返回失败提示。因为获取锁失败，意味着锁一定被同用户id下的其他线程占有了，即该用户id已经发起了下单请求，可以直接提前返回失败。

**4.锁的过期时间设置多久合适？设置短了/长了有什么问题？**
如何设置：应略大于“获取锁后，执行事务的平均时间”。可通过压测得出，通常为几百毫秒到几秒。
设置过短：业务未执行完，锁自动释放，导致其他线程进入，造成并发问题。
设置过长：锁长时间不释放，其他线程会长时间等待，降低系统吞吐量

# 6 秒杀优惠券优化：Redis Lua脚本快速判断秒杀资格+Redis Stream作消息队列+后台线程执行数据库操作

## 6.1 实现过程

**原优惠券秒杀过程：**

1.判断库存

2.判断一人一单

3.扣减库存

4.创建订单

**现在的实现过程：**

**A.在Redis的lua脚本中快速判断秒杀资格，返回判断结果：**

在Redis中维护两个缓存：优惠券的库存数量+优惠券的下单用户集

1.判断库存（库存在Redis中维护，String类型）

2.判断一人一单（优惠券对应购买用户在Redis中维护，Set类型）

3.扣减Redis库存（维护Redis，incrby -1）

4.增加到下单用户集（维护Redis，sadd）

5.将订单信息（用户id+优惠券id+订单id）发送到stream消息队列

6.返回判断结果（0表示下单成功）

**B.根据判断结果，如果成功，直接返回前端订单id；异常则业务失败**

**C.后台消费者线程异步过Consumer Group从Redis Stream中读取消息，异步执行数据库操作**：

提前创建一个单线程的线程池，该线程：

1.XREADGROUP阻塞读取消息（BLOCK 2000ms）

2.解析消息中的userId、voucherId、orderId

调用处理函数：

​	3.获取Redisson分布式锁（锁粒度：userId + voucherId）

​		开启数据库事务：

​			4.在数据库层面再次判断一人一单（防止消息重复消费）

​			5.扣减数据库库存（乐观锁）

​			6.创建订单（数据库层，唯一索引（userID+voucherId））

​		提交事务

​	释放锁

处理函数结束：

7.ACK确认消息

**D. PendingList异常补偿机制：**

当消息处理异常，未能成功ACK，消息会留在PendingList中。异常捕获后，消费者会优先从PendingList中重新读取未确认的消息并重试处理，确保消息不丢失。重试次数超过一定次数，写入到死信表中，并报警。

## 6.2 问题拷打

**1.为什么选择Redis Stream而不是JVM内存阻塞队列？**

JVM阻塞队列（如ArrayBlockingQueue）存在三个问题：

- **不支持持久化**
- **内存限制**
- **不支持集群：**消息只能被产生它的JVM所消费，不能负载均衡

**2.为什么选择Redis Stream而不是RabbitMQ/Kafka？**

1.轻量：项目已经依赖Redis，无需引入额外中间件，降低运维复杂度

2.可靠性已经足够了

**3.这样做的好处？（消息队列的优点）**

1.快速响应（异步）：主线程只需要投放消息就可以响应用户，数据库落库耗时操作交给后台消费者线程执行

2.流量削峰（削峰）：将高并发请求作为消息存储在消息队列中，然后消费者线程再自己慢慢的取出消息消费，避免了高并发请求打垮数据库

**4.消息可靠性如何保障？即怎么防止消息丢失？（消息可靠性）**

A 依靠MQ（Redis Stream）本身存储不丢失：

1.持久化：Redis本身支持持久化，重启后数据还在消息就不会丢失。生产环境我会开启AOF everysec。

2.高可用：采用主从节点+哨兵节点，避免单节点故障带来的影响。

B 消费者处理不丢失：

消息需要ACK后，才会从Stream中移除，处理失败会有重试机制。

**5.消息会不会重复消费？如何保证幂等性？（消息幂等性）**

可能会。比如消息处理成功但ACK失败，消息会留在PendingList被再次消费。

幂等性保障有三层：

**Redis层**：Lua脚本中用SISMEMBER检查Set，同一用户不会被重复记录

**消费者业务层**：先查询订单是否存在（一人一单检查），再配合Redisson分布式锁，即使重复消费也不会创建重复订单

**数据库层：**建立了（用户id+优惠券id）的唯一索引

**6.为何需要在后台线程任务中再次判断一人一单（消息幂等性）**？

保证幂等性。消息可能会重复消费（处理成功但ACK失败）。所以处理过程要再次在数据库层面判断。同时也是防御性编程，进行最后兜底。同时也是分层防御思想的体现（每层做好防御，不依靠其他层，保证安全）

**7.为什么要开启事务？（一致性）**

保证一致性，即支持崩溃回滚，不发生中间状态，比如扣减库存成功，但是创建订单失败

**8.分布式锁为什么要加在事务的外面？**

以免一个场景发生：先释放锁、但还没提交事务，于是其他的线程抢到了锁，看不到库存已经扣减了（因为事务没提交，默认可重复读，读不到没提交的事务），导致超卖。因此一定要事务提交，影响生效，才释放锁。

**9.如何实现事务的？**

@Transactional注解+Spring代理

**10.为什么需要lua脚本来判断秒杀资格？**

保证原子性。Lua脚本中包含判断库存、判断一人一单、扣减库存、记录用户、发送Stream消息共5个操作，这些操作必须原子执行（第一个维度：执行连续，中间不会去执行其他客户端的命令）

**11.Lua脚本怎么保证原子性？**

1.Redis是单线程执行命令的

2.Lua 脚本在执行时会被当成一个整体，由Redis主线程串行执行，执行期间不会插入其他客户端命令

**12.Lua 脚本只执行到一半，已经扣减了 Redis 库存，但还没写入 Stream，结果宕机了，怎么办？**

1.承认Lua的问题：Redis Lua 脚本保证的是执行期间不被其他命令打断，但不等价于数据库事务，不提供自动回滚能力。如果脚本执行过程中某一步失败，前面已经执行成功的写操作不会自动撤销。

2.使用定时对账的补偿机制：后台定时任务对比 Redis 的 `VoucherSet`（下单用户集）和数据库中的订单记录。如果发现 Redis 里记录了某人购买成功，但数据库过了 5 分钟还没订单，则触发回滚机制：增加redis库存，并从下单用户集移除用户；或重新补发消息。保证最终一致性。

**13.库存和优惠券对应购买用户这两个缓存是怎么设计的？以及与数据库的一致性策略？**

库存缓存：使用String类型，value为库存数量，在添加优惠券时，更新Redis缓存

购买用户集合：使用Set类型，value为用户ID集合

一致性策略：Redis作为权威数据源保证秒杀期间的一致性，Lua脚本中直接维护Redis缓存，异步线程负责将最终结果落库。

**14.什么是Consumer Group（消费者组）？为什么要用？**

**消息分发**：保证服务器集群环境下，消息不会被重复消费

**游标**：Redis自动维护每个消费者组的消费偏移量，重启后从上次位置继续消费

PendingList：已投递但未ACK的消息会记录在PendingList中，支持异常重试

**15.消费者线程处理时为什么要加Redisson锁？**

简介：保证多线程并发环境下，查询订单+创建订单这个过程的原子性（这里指的是执行的连续性，即同时只能有一个线程访问临界区）

如果是单服务器实例，的确冗余，采用的线程池只有一个单线程，不可能有并发的风险；

在服务器集群情况下，如果是正常的分发消息，也没有必要，因为分发的是不同的消息，不同消息一定对应不同的userID+voucherID，而锁实现的粒度是userID+voucherID，也不会有并发；但存在一个极端的场景，如果没有锁，线程A被分发到某条消息X用户买了Y商品，成功创建订单，事务尚未提交时，假如此时断联；长时间，该消息没有被确认，假如被另一个实例上的线程XCLAIM获取到，此时由于事务没有提交到，数据库查询不到X买了Y这个订单，所以它也成功创建了订单。最后事务提交两个订单被创建，导致了一人多单。

同时也是分层防御思想的体现（每层做好防御，不依靠其他层，保证安全）

**16.为什么要用单线程消费？不用多线程来消费**

单线程就够用了。秒杀场景，大部分的并发请求都在Redis层被处理掉了，只有少部分人可以成功，消息数量不会太多。

**17.消息多次落库失败怎么办？**

落库失败消息没有被ACK，仍然保留在消息队列中。异常会触发PendingList补偿机制，会从PendingList中拿出消息进行再次消费重试

重试到一定次数，还不行，会记录到异常表，后续人工补单等

**18.订单结果数据库里还没有，前端查询订单id怎么办？如何区分处理中和真的没有**

在Redis中存订单状态，FAILED和SUCCESS和PROCESSING。查的时候先查redis看是什么。

**19.死信表一般记录什么？**

记录消息ID、订单ID、用户ID、商品ID、原始消息体、失败原因、重试次数、处理状态、时间戳，方便人工补偿和审计。

**20.消息积压怎么办（消息积压）**

1.监控Stream长度，超过阈值告警

2.提高消费能力，增加消费者线程数量

3.减少生产速度，入口处采用限流

# 7 自定义注解+AOP+Lua实现令牌桶限流

## 7.1 实现过程

简介：**自定义注解 `@RateLimit`** 标记需要限流的接口 → AOP拦截带注解的方法 → 执行 **Redis Lua脚本**，令牌桶算法判断是否超过限流阈值 → 超过则直接返回失败，未超过则放行执行业务逻辑。

### 7.1.1 自定义注解@RateLimit

定义一个注解，包含以下参数：

- `capacity`：桶容量，即最大令牌数，也是允许的最大突发请求数（默认10）
- `rate`：每秒生成的令牌数，即稳态下的限流速率（默认10）
- `prefix`：限流key前缀，默认使用方法名
- `limitType`：限流类型，支持`USER`（按用户限流，每个用户独立计数）、`GLOBAL`（接口全局限流，所有用户共享计数）和`PARAM`（按请求参数限流）

### 7.1.2 AOP切面@RateLimitAspect

使用`@Around`环绕通知拦截所有带`@RateLimit`注解的方法，执行流程：

1. 通过反射获取方法上的`@RateLimit`注解及其参数
2. 构建限流的Redis Key：
   - 按用户限流：`rate_limit:{prefix}:{userId}`
   - 全局限流：`rate_limit:{prefix}`
   - 按参数限流：`rate_limit:{prefix}:{paramValue}`
3. 调用Redis执行Lua令牌桶脚本，传入key、桶容量、令牌生成速率、当前时间戳
4. 根据脚本返回值判断：返回0表示被限流（无令牌），直接返回`Result.fail("请求过于频繁")`；返回1表示放行，执行`joinPoint.proceed()`调用目标方法

### 7.1.3 Lua脚本令牌环算法判断是否限流

核心数据结构：**Hash**，存储两个字段：`tokens`（当前令牌数）和`lastRefill`（上次补充令牌的时间戳）。

脚本执行逻辑（原子执行）：

1. **读取桶状态**：`HGET key tokens` 和 `HGET key lastRefill`，获取当前令牌数和上次补充时间
2. **首次初始化**：如果key不存在（首次访问），初始化为满桶（tokens = capacity）
3. **补充令牌**：根据距离上次补充的时间差，按速率计算应补充的令牌数，累加到当前令牌数（不超过桶容量）
4. **判断是否有令牌**：如果 tokens <= 0，返回0（被限流）
5. **消耗令牌**：tokens - 1，更新Hash中的tokens和lastRefill
6. **刷新过期时间**：`PEXPIRE key expireMs`（桶填满所需时间的2倍），防止冷数据占用内存

## 7.2 问题拷打

**0.为什么要限流**

防止恶意用户或者脚本高频刷接口，浪费Redis资源。在Controller入口层就进行限流。

**1.为什么选令牌环限流**

允许突发流量，更加适合当前秒杀场景。刚开始桶是满的，可以允许突发流量通过，过一会令牌空了，只能一点一点通过。

**2.为什么不用Guava RateLimiter**

Guava RateLimiter是JVM本地限流，在集群环境下每个实例独立计数。比如限制每秒10次，3个实例加起来实际允许30次。Redis限流是分布式的，所有实例共享同一个计数器，能精确控制全局的请求速率。

**3.限流的粒度怎么设计**

秒杀接口使用**按用户限流（USER）**。防止单个用户（或脚本）刷接口，但不影响其他正常用户。如果用全局限流，正常用户可能因为其他用户的高频请求而被误拦

**4.限流key的过期时间怎么设计**

设置为桶填满时间的两倍。确保桶有足够时间自然恢复到满状态（不然还没满就删，例如小于1倍，下次访问直接就是满桶），同时不活跃用户的key也能在合理时间内被自动清理，不占用内存。

**5.为什么用Lua脚本：** 

上述5步操作必须原子执行。如果分开执行， 在高并发下可能出现：令牌只有一个，线程A获取到令牌还未扣除，B也获取到令牌，两个都放行，实际超限。

**6.为啥要用注解+AOP，不用拦截器？**

拦截器更适合全局，我希望针对接口灵活配置限流
